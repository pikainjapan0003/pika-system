九、PRIVATE POC 的規劃方式

本輪先規劃，不直接實作或發布。

第一個 POC 應是最小可工作的完整流程，而不是只做漂亮畫面。

建議以一間合成店鋪與少量假資料，驗證：

店主身分
→ 管理端查看／維護商品
→ 在私人測試環境模擬客人看商品與下單
→ 訂單確實保存
→ 客人用既有方式查詢自己的假訂單
→ 店主能在後台看到該筆訂單。

具體切片與實作顺序由你依 repo 和 Sites 限制決定。

OCR、物流、上傳與成本功能：
先保留入口及依賴盤點，安排下一個最小切片。
本輪不因第一個 POC 沒全做，就把仍需功能刪掉。

外部 OCR／物流初期使用 fixture、sandbox 或 mock，清楚標記。
mock 通過不是正式外部整合通過。

尤其不要產生真物流單、付款、簡訊、郵件或其他客戶側副作用。

私人網站可见性與應用程式店主授權是不同事情。
即使平台 preview 私有，也不能因此把管理 API 改成無條件放行。
若平台管理員仍可讀取站點，不能聲稱「只有本人」已由平台私有設定完全保證。

目前不公開客人入口，但要保留未來公開商品／下單與私人管理後台的分離能力。
不因 POC 私有而重寫成只有後台、丟掉客人流程。

若 PRIVATE 限制導致外部 webhook 等無法測試，列為未驗證或 blocker，不為通過測試擅自改公開。
