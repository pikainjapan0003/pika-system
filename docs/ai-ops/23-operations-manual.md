# 店主操作手冊

- 更新日：2026-09-27
- 適用對象：店主／後台操作人員
- 本遷移分支已移除技能地圖、首登問卷與開通機制；正常功能依指定店主權限直接使用。
- 私人 POC 僅操作合成資料；真付款／出貨／通知、自動票價／匯率仍停用，下文保留的其他業務操作不代表本階段已啟用。實際進度見 `../sites-migration/PHASE1-PLAN.md`。

## 最短流程

1. 到「設定」填店鋪進貨匯率與可用物流方式。
2. 新增商品，需要看毛利時一併填成本與交通路線。
3. 複製商品分享連結給客人。
4. 到「訂單」確認新單。
5. 撿貨、包貨、出貨並更新狀態。
6. 展開訂單查看已定格毛利，或到首頁看每月毛利。

## 1. 老闆首頁與每月毛利

1. 登入後先看首頁的「老闆今日重點」。
2. 「今日／本週訂單」是筆數；「已定格毛利小計」只加總已有金額快照的訂單。
3. 「待確認訂單」是訂單流程狀態；「毛利待補拍」與「尚無快照」是成本資料狀態，三者意思不同。
4. 點「處理訂單」可逐筆處理。
5. 點「查看每月毛利報表」後選月份，可看該月訂單數、已定格毛利、待確認與尚無快照數。

> 截圖留白 1：首頁六張重點卡與「查看每月毛利報表」。

## 2. 上架與分享商品

1. 點下方「商品」，再點「新增商品」。
2. 填商品名稱、一般售價、庫存與規格。
3. 需要看成本毛利時，同時填商品日圓成本並確認店鋪進貨匯率。
4. VIP／批發／夥伴價可以留空；留空會使用一般售價，不會當成 0 元。
5. 商品免攤交通時打開免攤；否則選擇已有成本資料的路線。
6. 儲存後確認商品已啟用。預估毛利顯示「待確認」時，先補齊成本資料。
7. 在商品卡點「複製分享連結」，把連結貼給客人；系統不會自動發訊息。

> 截圖留白 2：新增商品與成本欄。
>
> 截圖留白 3：商品卡的分享連結。

## 3. 接單與確認

1. 客人從分享頁填資料下單，不需店主代操作。
2. 點下方「訂單」，展開新單核對商品、數量、金額與取貨方式。
3. 依實際進度更新：待確認 → 待付款 → 備貨中 → 已出貨 → 已完成。
4. 成本快照顯示「待確認」時，補齊商品成本、店鋪匯率與路線後，可按一次「補拍」。
5. 「尚無快照」通常是舊單，也可補拍一次。補拍後會永久定格並留下時間。

> 截圖留白 4：新單、狀態選單與補拍按鈕。

## 4. 撿貨、包貨與出貨

1. 到訂單頁下方的撿貨／出貨工具。
2. 開啟撿貨清單或下載撿貨檔，依商品與規格分揀。
3. 包裝前再次核對客人、品項、數量與取貨方式。
4. 實際交寄後才把出貨狀態改為「已出貨」。
5. 客人取貨／交易結束後再改為完成。

> 截圖留白 5：撿貨清單、出貨工具與物流狀態。

## 5. 查毛利

1. 在訂單列表展開該單，找到「成本與單件毛利」。
2. 「金額」表示建單或補拍時已定格；以後改成本或匯率不會改舊單。
3. 「免攤」表示交通成本以 0 定格，而且畫面會明確標示免攤。
4. 「待確認」表示當時成本資料不足，不能當成 0。
5. 「尚無快照」可在資料完整後補拍一次。

> 截圖留白 6：金額、待確認、免攤、尚無快照四種狀態。

## 6. 行程與交通成本

1. 到「設定 → 行程與路線管理」。
2. 先建立行程；行程匯率可以留空，但相關商品成本會顯示待確認。
3. 在行程內新增路線，填預估件數、電車、油資、停車、ETC、紙箱、日本境內運費與包裹數。
4. ETC 必須自己填；沒有費用時填 0，系統不會自動用件數代填。
5. 商品沒有免攤時，在商品表單選擇對應路線。

> 截圖留白 7：行程與路線中的 ETC、日本境內運費、預估件數。

## 7. 店鋪匯率與銀行參考匯率

1. 到「設定 → 店家設定」填店鋪進貨匯率。
2. 到「設定 → 銀行匯率參考」查看已核可銀行的日圓即期賣出價、來源與掛牌時間。
3. 抓不到資料時會顯示「暫時不可用」，不會用 0 或舊值冒充。
4. 點某家銀行的「套用」只會把參考值填進輸入框，仍要自己確認並按儲存。
5. 參考匯率不會自動覆蓋店鋪匯率或行程匯率。

> 截圖留白 8：多銀行參考表、掛牌時間與「套用」。

## 8. 客戶管理與客戶詳情

1. 到「設定 → 客戶管理」，不需要額外開通。
2. 建立客戶代號、姓名、可選手機、等級與常用門市。
3. 客戶列表預設遮罩；需要時點「顯示完整」，系統會留下揭露紀錄。
4. 點客戶卡右側「詳情」，可看基本資料、常用門市與該客戶的訂單歷史。
5. 詳情頁顯示的是訂單定格毛利；待確認不會顯示成 0。
6. 後台新增訂單時可用代號或姓名搜尋客戶；選中後會帶入常用門市。
7. 如果在訂單內手動改選門市，手選結果優先。

>

## 9. 功能存取與缺少成本資料

商品、訂單、客戶、行程、OCR 與報表由指定店主直接使用，不再有技能問卷、套餐或解鎖入口。登入與資料歸屬校驗仍在後端執行。

成本顯示「待確認」時，請檢查商品成本、採購匯率與交通路線所需資料；缺少資料不可當成 0。私人測試版未核准的真付款、真出貨、通知與自動來源仍停用，移除技能機制不會啟用它們。

## 10. 匯出客戶與訂單

1. 客戶與訂單匯出預設為遮罩版。
2. 匯出前會顯示筆數並要求確認。
3. 明文版要再勾一次確認；下載後請妥善保管並在使用後刪除。
4. 訂單毛利待確認時，檔案會寫「待確認」，不會寫成 0。
5. 匯出與顯示明文都會留下操作紀錄，紀錄不保存明文個資。

> 截圖留白 12：遮罩版／明文版的二次確認。

## 11. 賣貨便出貨 CSV／XLSM

1. 到「訂單」頁的賣貨便匯出區，先選擇要處理的日期範圍並預覽。
2. 畫面會分成「可匯出」與「不可匯出」；不可匯出的訂單會列出缺少資料或格式不符的原因，請先修正再重試。
3. 只勾選尚未出貨且顯示可匯出的訂單，再按「準備匯出 N 筆」。
4. 系統會顯示「將匯出 N 筆明文個資」。確認姓名、手機與門市資料只會用於本次出貨後，勾選「我確認本檔僅用於賣貨便出貨」。
5. 按「確認並下載 CSV」。下載與明文匯出都會留下操作紀錄，但紀錄本身不保存明文個資。
6. 檔案含收件人明文資料，完成賣貨便匯入後請立即刪除，不要轉傳或留在共用裝置。
7. 若要使用官方範本，完成同樣的二次確認後選擇「XLSM」下載；檔名應以 `.xlsm` 結尾。
8. 用桌面版 Excel 開啟 XLSM，確認沒有格式修復警告，並確認「填寫說明」`B1=1.4`、`訂單匯入` 工作表與官方 10 欄順序一致。
9. 只用假資料在賣貨便測試／草稿入口預覽匯入結果，不要按正式出貨；驗收後立即刪除 XLSM。

## 12. 客戶購物金

1. 到「設定 → 客戶管理」，點客戶卡右側「詳情」。
2. 在「購物金餘額」查看目前餘額；下方「最近流水」會列出發放、調整、訂單折抵與取消回沖。
3. 要新增購物金時，在「發放／調整」選「發放（正數）」，輸入金額與原因代碼；備註可不填。
4. 要人工修正時選「調整（可正可負）」。負數不能讓餘額低於 0，系統會直接阻擋。
5. 按「預覽並確認」先看變動前與變動後餘額；確認無誤後，再按「確認變更」。
6. 不要重複快速送出；每次完成後，確認餘額及最近流水都已更新。
7. 到「訂單」新增訂單，先選客戶，再在「購物金折抵」輸入金額；建立後會顯示折抵列與折抵後應付現金。
8. 訂單使用購物金時，系統會自動建立「訂單折抵」流水；取消該訂單時按「取消訂單」再按「確認取消」，系統會自動建立「取消回沖」，不要另外手動補一筆。
9. 購物金流水是帳本，不能直接修改或刪除；發現錯誤請用「調整」留下相反方向的新紀錄。

> 截圖留白 16：最近流水的發放、折抵與回沖。

## 13. 付款末五碼人工對帳

1. 客人可在待確認／待付款期間填付款末五碼；這只是對帳線索，不會自動改成已付款。
2. 後台可用末五碼、金額與狀態篩選，再由店主核對實際入帳。
3. 末五碼不是完整帳號，也不是付款證明。

## 操作提醒

- 看到「待確認」不要自行當成 0 記帳。
- 訂單編輯不等於已通知客人；訊息模板也只會複製，不會自動發送。
- 取消訂單會保留紀錄；有物流或完成紀錄的訂單不要隨意刪除。
- 人工功能驗收延後；尚未驗證的 Excel 開檔、官方匯入及真貨態不可當成已通過。

## BATCH-21 incident response quick chapter

### If the app reports a database outage

1. Open `/api/healthz` and record the HTTP status and the fields `status`, `database`, `latestMigration`, `schemaVersion`, and `buildTime`.
2. If the response is 503, do not retry migrations against the live database. Save the response and deployment log for review.
3. Check the deployment database connection in the hosting dashboard without copying its secret into chat or a report.

### If a backup or integrity check is requested

Use the read-only scripts in the owner acceptance checklist. They require an explicit disposable database or dump path and reject Replit/production-looking URLs. A non-zero integrity result is an incident signal; do not repair rows from the verifier.

### If a public-data or privacy incident is suspected

Stop publishing changes, preserve the request ID from the response header, and record the endpoint and time without copying tokens or personal data. Reproduce only with synthetic data, then escalate with the raw status and sanitized server log. Never paste a bearer link, database URL, or cleartext export into the incident report.

### Recovery closeout

After the owner approves a fix, run the relevant disposable-database tests and CI checks, publish once, and verify `/api/healthz` plus the affected public endpoint. Record the commit, CI run URL, publish time, and remaining risk in the batch report.
