# 客戶刪除方案題卡

日期：2026-07-31  
目的：釐清有購物金帳本與歷史訂單後，客戶資料應如何「刪除」。本文件只做設計比較，不實作。

## 現況事實

- `customers` 目前沒有 DELETE route，也沒有 `deleted_at`／封存欄位。
- `orders.customer_id` 使用 `SET NULL`，所以單看訂單關聯，客戶刪除後歷史訂單仍可保留。
- `store_credit_transactions.customer_id` 使用 `RESTRICT`；只要客戶曾有任何購物金流水，PostgreSQL 就會拒絕硬刪。
- 購物金採不可覆寫餘額的流水帳；grant、adjust、spend、reversal 與 audit 是日後對帳依據。
- 客戶 PII 包含姓名、手機、常用門市名稱／地址／電話及自由文字備註。

## 三個方案

| 方案                  | 作法                                                                    | 優點                                       | 缺點／風險                                                 | 實作量 |
| --------------------- | ----------------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------- | -----: |
| A. 硬刪＋連鎖刪除     | 刪 customer，同時刪購物金流水；orders 的 customer_id 變 NULL            | 資料庫看起來最乾淨                         | 破壞不可竄改帳本、失去對帳依據、退款／爭議無法追溯；不建議 |     高 |
| B. 匿名化封存（建議） | 保留 customer 主鍵與流水；清除／替換 PII，標記 archived；停止新訂單選用 | 帳本與訂單關聯完整，個資最小化，能保留稽核 | 需定義匿名代號、保留期與哪些欄位可留；UI 要排除封存客戶    |     中 |
| C. 純軟刪             | 加 `deleted_at`，所有原資料原樣保留，只在一般 UI 隱藏                   | 變更小、可還原                             | PII 仍完整存在，不足以回應真正的刪除／個資最小化要求       |     低 |

## 建議：B，匿名化封存

這是唯一同時保住帳務證據與降低個資留存的方案。建議資料語意：

1. customer id 不變，購物金與既有訂單的關聯不動。
2. 設 `archived_at`；一般客戶搜尋、後台建單選擇器及分級定價名單預設排除 archived。
3. `name` 改為不可逆、非個資的顯示值，例如「已刪除客戶 #123」。
4. `phone`、常用門市四欄及 notes 清為 NULL。
5. `code` 改為 store 內唯一的 opaque archive code，不能從原代號推回。
6. tier 回到 `general`，避免封存資料繼續影響任何新交易。
7. 購物金帳本與 audit log 不改內容；現有 audit target 必須維持 opaque，不補入姓名或手機。
8. 有正餘額時不可直接封存：先走已拍板的餘額處理流程，或由老闆另行決定退款／失效規則。

## 操作流程建議

1. owner 在客戶詳情按「封存並移除個資」。
2. 畫面先列影響：歷史訂單與帳本會保留、姓名手機與常用門市會清除、操作無法復原。
3. 若餘額不為 0，先阻擋並顯示「請先處理購物金餘額」；不可默默歸零。
4. 第二次輸入確認文字後才執行。
5. server 在同一 transaction 內匿名化＋寫 audit。
6. 回應只含狀態與 opaque customer id，不回已清除的 PII。

## Audit 建議

新增受控 action，例如 `archive_customer_and_redact_pii`。target 只放 `customer:{id}`；不得放 code、姓名、手機、門市或原備註。稽核需要記錄 actor、store、action、target、時間，但不保存被清除個資的副本。

## 保留與匯出

- 歷史訂單與購物金帳本屬金流／對帳資料，保留期限要由老闆依實際會計與法規需求拍板。
- 封存前如需資料可攜，應使用 owner-only 匯出、二次確認及 audit；不得把完整個資寫進一般 server log。
- 過了拍板的保留期限後，能否刪除帳本或只保留彙總，也屬法務／會計決策，不能由程式自行猜。

## 待老闆拍板

1. 客戶要求刪除時，有正購物金餘額要退款、轉為失效，還是禁止封存直到人工歸零？
2. 歷史訂單及購物金流水保留幾年？
3. 匿名化後是否允許用同一手機重新建立全新客戶？建議允許，因舊手機已清除。
4. 是否需要短期可撤銷期？建議不提供，因匿名化應不可逆；誤操作靠二段確認防止。
5. 封存客戶是否仍可在歷史報表看到「已刪除客戶 #ID」？建議可以，但只顯 opaque 標記。

## 明確不建議

- 不可為了讓 DELETE 成功而把購物金 FK 改成 CASCADE。
- 不可把 PII 複製到 audit log 後再從 customer 刪除。
- 不可用「畫面隱藏」冒充個資已刪。
- 不可在餘額不明時默認為 0。
